## How the items are made

**`fix_bug` and `debug_line` with a bug.** Each is one row of `ml/data/dataset.jsonl` with `source: "A"`, no augmentation, one operator, label a real class. `op_id` and `planted` are the row's own. Rows from `amb_*` operators and from the `AMB` source are never used (they carry two labels). `OTHER` is not planted (no class to credit). Four rows per class are picked, spread over different problems and operators, short diffs first; two become `fix_bug`, two `debug_line`.

**`bug_lines`.** A line diff between the mutant and the correct variant it was made from. Both are reprinted by the generator and put into K&R braces with 4-space indent (`tidy`), and the builder refuses a row if `tidy` changes the syntax tree. Lines that were only inserted are the bug lines; for a deleted statement the line before (and the line after, unless it is `}`) is used. The `;` of an M07 `if (c);` item gives three bug lines (`if`, `;`, `{`) because the generator prints them as three lines.

**`debug_line` extras.** `explain` is a fixed one-line reason per `op_id` (one per operator, written by hand, with a class-level fallback) followed by "It should read: …" taken from the diff. `fix` = `{code, changed_lines}` with the correct variant (same layout as the buggy code). `allow_no_bug` is true everywhere.

**No-bug items.** A correct variant reprinted the same way as the buggy ones, so the layout never says which is which. `planted`, `op_id`, `fix` are null, `bug_lines` is `[]`. Id form: `dl_<problem>_ok_01`.

**`complete_snippet`.** From a problem's own correct variants (author's layout kept). Hole kinds: `loop_init`, `loop_rel`, `loop_update`, `acc_init`, `index`, `bound_update`, `rec_arg`, `base_cond`, `branch_rel`, `return_value`, `cast_expr`. Each hole has the right text plus up to two wrong choices from a fixed list of tempting variants (`<=` for `<`, `i--` for `i++`, `n` for `n - 1`, `(float)(a / b)` for `(float)a / b`, …). A wrong choice is kept only if, filled in alone, it still parses and fails a test. Then every combination of choices is run and wrong choices are removed until exactly one combination passes. Up to 3 holes per item. The second item of a problem comes from another correct variant and prefers other hole kinds.
- `exposes` = classes whose predicate (C1/C2 `holds`) fires on some wrong fill but not on the right code, plus the classes each hole kind is for, limited to the classes in the problem's `exposure`.
- `choices` are shuffled with the item id as seed, so the right one is not always first.

## Matches to the contracts, and mismatches

1. **The right answers.** `Hole` has no answer field and the model forbids extra keys, so the reference fill is stored in `fix`: `{"code": <full correct code>, "answers": {"h1": "0", …}}`. `CodeItem.fix` is an open dict and `PublicCodeItem` drops it. S3 must not send `fix` for a `complete_snippet` (the public view already leaves it out).
2. **S2 (`server/app/pipeline.py`, `code_item_rule`).** It reads `type`, `item_id`, `planted`, `starter`, `bug_lines`; all are there, with the types it expects. Tested with the real file: a passing submission → `correct`; the starter unchanged → `wrong` and `bug_lines_unchanged: true`; a shifted starter → `bug_lines_unchanged: false`. No mismatch. Two things S2 should know:
   - Its `bug_lines_unchanged` compares line N of the submission with line N of the starter. If the learner adds or removes a line above a bug line (common for deleted-statement bugs such as D05 "no base case", where `bug_lines` is the line before and after the gap), it says "changed" even though the bug may still be there. The top-1 ≠ planted rule is unaffected.
   - `item["starter"]` for `fix_bug` is in the tidied layout; `/attempt` sends the learner's text, which has the same layout unless they reformat.
3. **`debug_line` public view.** `PublicCodeItem` gives `code`, `allow_no_bug`; no `planted`, `bug_lines`, `fix` ✔ (tested).
4. **Hole `line`** is 1-based in the starter, as in the 05 example.

## Skipped or weak

- **`OTHER` is never planted**, and no `CORRECT` near-miss is used for no-bug items.
- **No two-bug, augmented or `AMB` code.** M01/M08 items use `m01_*` / `m08_*` operators, not the `amb_*` twins.
- **P13 has one `complete_snippet`.** Its only hole is the whole `return` expression (the three cast placements).
- **Deleted-statement bugs** (a missing base case, a missing update, a missing swap temp) have fuzzy `bug_lines`; 8 of the bug items have 3 bug lines and 11 have 2 (the other 49 have 1). A learner who taps any of them is correct.
- **`exposes` is a heuristic** (predicates plus the hole kind); it is not checked against a learner. The `complete_snippet` wrong choices are the first tempting variants that fail, not data on what students type.
- **Layout.** Buggy code is the generator's reprint, so some expressions have extra parentheses (`i < (n - 1)`), which the author's variants do not. Nothing in the item says which line has the extra parentheses, but a learner may notice.
- **Not validated with learners.** "Correct" only means: fails/passes the problem's tests on the interpreter (fix code and right fills also on gcc). Mutants are interpreter-only (some use undefined C, e.g. uninitialised reads).
- **No DeepSeek, no installs.**

## `--check` rules

Schema (`CodeItem`, public view); unique ids; every problem exists. Bug items: planted ∈ the 17 classes, `op_id` is a real operator that produces that class, buggy code fails a test, `holds(op_id)` is true, the code's tree equals an unaugmented dataset row of that problem and op, `bug_lines` equal the diff against the fix, `fix.code` is a correct variant and passes on both backends. No-bug items: passes, is a correct variant, no op id. Snippets: `____` count = holes; each hole line has a `____`; filling the answers gives `fix.code`; exactly one choice combination passes; every wrong choice fails alone; `exposes` non-empty. Targets: as in the table above.
