# S2 — Diagnosis pipeline and routes

`pytest tests/S2 -q`: 26 passed (run three times; 9–13 s each).

## Built

| File | What it is |
|---|---|
| `server/app/pipeline.py` | The pipeline as plain functions, no FastAPI: gate (G1) → `runner.run_tests` + `runner.trace` (A1) → `extract` (F3) → `Diagnoser.proba / contributions / knn_distance` (M1) → optional learner prior and predict item (D1) → probe answers (D1) → `decide` (M1) → `build_evidence` (M1) with the fixers (R1) for the top-3 only. Also `run`, `analyse`, `diagnose`, `attempt`, `code_item_rule`, `warm`, `get_problem`. |
| `server/app/routes/attempt.py` | The HTTP layer: `POST /run`, `/attempt`, `/probe/answer`, `/lab/diagnose`. Rewritten. |
| `tests/S2/` | `conftest.py` (session app + warm-up), `test_s2.py` (26 tests). |

## Endpoints

| Endpoint | Behaviour |
|---|---|
| `POST /run` `{problem_id, code, sample_only?}` | `{gate, trace, tests, model_version, latency_ms}`. No diagnosis. Gate failure → `trace` and `tests` are `null`. |
| `POST /attempt` `{learner_id, problem_id, code, events[], code_item_id?, prediction?}` | `{attempt_id, gate, trace, tests, diagnosis, model_version, latency_ms}` (+ `code_item` when `code_item_id` names a known item of that problem). Gate failure → `diagnosis: null`, as in the fixtures. The attempt is kept in memory (last 1,000) for `/probe/answer`. |
| `POST /probe/answer` `{learner_id, attempt_id, probe_id, answer, problem_id?, code?, probe_answers?}` | `{diagnosis, model_version, latency_ms}`. Uses the stored attempt. If the id is unknown (server restarted) and `code` is sent, the code is re-analysed (the app does send `problem_id` and `code`); then only the answers in `probe_answers` plus this one are applied. Answer not an option / unknown probe → 422 `{"error"}`. A probe id answered twice counts once (first answer stands). |
| `POST /lab/diagnose` `{problem_id, code, prediction?, probe_answers?[]}` | `{gate, trace, tests, diagnosis, ...}`. Stateless: no learner prior, nothing stored, answers applied in order. |

Errors return `{"error": "<where> failed (<ExceptionType>)"}` with 422/404/500; no stack trace, no paths.

### Which path answers

1. Problem is in the ML bank (`ml/problems/main`, `ml/problems/dsa`) **and** a `ml/artifacts/diagnoser_*` exists → the pipeline.
2. Otherwise, if the older rule-based code (`server/app/*_rules.py`, written by Arnav for the app: P18–P23, and the bank ids when there is no artifact) knows the id → that path, unchanged (`model_version: "rules-v1"`).
3. Otherwise → the fixture for that id (`GATE`, unknown ids), unchanged.

### `/probe/answer` also lives in `routes/probe.py` (overlap, not edited)

`routes/probe.py` (Arnav, commit d30f454, rule-based `loops_rules.resolve_probe` for P03 only) registers the same path. Routers load alphabetically and the first registered path wins, so `attempt.py` answers and `probe.py` is never reached. I did not touch it. It also imports `_find_problem` from `attempt.py`; that name is kept. I1 may delete `probe.py` (and `trap.py`/`intervene.py` stay S1's/R2's business). Who wrote the other files in `routes/`: `attempt.py`, `probe.py`, `trap.py`, `intervene.py` all come from Arnav's commits (135ca9a, d30f454, 03722a8) before the package split; none is in a `notes/*.md`.

## Decisions where the plans are silent

1. **No learner prior unless S1 provides one.** `pipeline.learner_prior_fn` is a module-level hook (`callable(learner_id) -> {class: P(active)} | None`). While it is `None`, or returns `None`, `prior()` is skipped entirely. Reason: `prior()` with no history applies `POPULATION_PRIOR ** 0.3` to the 17 misconceptions only, which multiplies CORRECT and OTHER by about 2 relative to everything else; for the stateless lab and for a learner with no history that is a bias, not a prior. S1 sets the hook when the store exists. Lookup errors are logged and ignored.
2. **Predict item.** `prediction` (body of `/lab/diagnose` and `/attempt`) or an event `{"type": "predict" | "prediction" | "predict_answer" | "predict_item", "payload": {"answer"| "value"| "prediction"}}` is scored with `ml.bayes.update` against `problem.predict_item` before probe answers; a "YOU PREDICTED" evidence item is added. The event name is a guess (the app's event list is not in the contracts).
3. **Novelty is recomputed on the current posterior** (`novelty.assess(knn_dist, posterior, tau_d, tau_p)`), so after a probe `p_max` is the new top probability, not the code model's.
4. **Fixers (R1) run only for the top-1 class** (fix sentence, status `confident` or `two_bug`) and, for the two-bug check, for top-1/top-2 when `p2 >= 0.25` and both are misconceptions. They are skipped when the request has already used 150 ms (`FIX_BUDGET_MS`). The fix sentence is not added for `ambiguous` (the code is identical for both explanations) or for `correct`.
5. **Two-bug check** (03 §5.5): fix(top1) alone fails, fix(top2) alone fails, and fix(top2) on top of each of fix(top1)'s candidates passes. R1 has no composition function, so this uses `ml.learner.fixer._candidates` (private) and `fixer.probe`. Checked only for not crashing; no real two-bug program was run.
6. **Evidence** is for the top-1 class; for `correct` with a `latent` it is for the latent class; plain `correct` has `evidence: []` (as in the fixture). `two_bug` adds one model item for the second class.
7. **Trace features are dropped when the interpreter says `parse_error` or `unsupported`**: `extract(problem, code)` with no trace (groups B and R NaN), the same as the 15% dropout rows in training.
8. **Code items (05 §4).** `code_item_id` is looked up in `ml/data/code_items.json` (C4 has not built it: `notes/C4.md`), reread when the file changes. Unknown id, or an item of another problem → a normal attempt, no `code_item` key. The response gains `code_item = {item_id, type, response, apply_diagnosis, ...}`:
   - `complete_snippet`: `apply_diagnosis: true`, `response: null` (a normal attempt).
   - `fix_bug`, all tests pass: `response: "correct"`, `apply_diagnosis: false`, `g, s = 0.35, 0.15` (from `params.ITEM_GUESS_SLIP["fix_bug"]`), `planted`.
   - `fix_bug`, top-1 ≠ planted, in the misconceptions, `p ≥ 0.5`: `response: "other_bug"`, `other: <class>`, `apply_diagnosis: true` (the learner wrote it).
   - `fix_bug`, anything else (planted bug still there, or an unclear failure): `response: "wrong"`, `apply_diagnosis: false`, and `bug_lines_unchanged` (true when every line in `bug_lines` is the same as in the item's `starter` ignoring white space).
   The knowledge update itself is S1/S3's; S2 only supplies the verdict.
9. **The gate runs on the learner's text and the pipeline passes `gate.normalise(code)` on** (G1's note), so smart quotes do not reach the interpreter.
10. **Responses are serialised with `json.dumps`** (a `Response`), not FastAPI's encoder: a trace of 2,000 steps took 100–350 ms to encode and pushed the slowest requests past 500 ms.
11. **Sync handlers** (`def`, not `async def`), so FastAPI runs the CPU work in its thread pool and one slow request does not block the loop.

## Contract problems and open issues

1. **03 §5.5 and §6.4 disagree on when to stop probing, and one probe can end below 0.85.** `decide` calls a case `confident` when `p1 ≥ 0.75` **or** `p1 − p2 ≥ 0.25`; §6.4 says stop at 0.85. After the first probe (`P_T1_b`) an M01 believer reaches 0.83 and an M08 believer 0.52 (its answer "4" is the correct one, so it only lowers M01); both are reported `confident` with no further probe, because `decide` only needs a lead of 0.25 over the runner-up. Two probes always reach ≥ 0.85, which is what the acceptance line says; but a demo that wants "ask until 0.85" would need `decide` to use `POSTERIOR_STOP` for twin cases. `decide.py` is M1's; not changed.
2. **The model is under-confident on the real dataset: temperature T = 2.447 and ECE gets worse (0.034 → 0.363).** From the `python -m ml.model.train` run I made (below). Temperature is fitted on grouped-CV logits (log-loss 2.65: a new problem is much harder than a seen one) and then applied to rows that look like the training problems. Visible effect: a plain M07 (stray semicolon) scores 0.72 band "Possible" and a correct program 0.76; the hard twin sits at 0.37/0.35 instead of ~0.45 each. `tau_p` came out at 0.29. M1/I1 should look at it (for example fit T on in-distribution OOF or cap it); S2 uses `Diagnoser.proba` as is.
3. **`POST /probe/answer` request shape.** 03 §11 lists `{learner_id, attempt_id, probe_id, answer}`; the app also sends `problem_id` and `code`. Both are accepted.
4. **`/problems` and `/problems/{id}` are marked S2 in `server/READY.md` but are not in S2's "Owns"** (06 §3 gives S2 `pipeline.py` and `routes/attempt.py` only). They still answer from fixtures. Fixture `problems.json` also contains P18–P23, which are not in the ML bank. READY.md rows for `/run`, `/attempt`, `/probe/answer`, `/lab/diagnose` should read "live" (W0/I1's file; not edited).
5. **Attempts are in memory only.** A restart loses them; the stateless replay (code in the request) covers it. No SQLite (S1). `/attempt` does not update any knowledge state; `learner_id` is only passed to the prior hook.
6. **Reasoning text is not wired** into `/probe/answer` or `/attempt`. T2's `read()` + `ml.bayes.apply_text` belong to S3's `/reason`. The attempt store exposes the `Analysis` object (`routes/attempt._recall(attempt_id)["analysis"].base` is the posterior before probes) if S3 wants to import it.
7. **Large traces.** Q13's response is 1.3 MB (2,000 steps; string `vars`). A1 owns the shape; the pipeline does not truncate. The app's phone link may care.
8. **Interpreter runs every test twice per request** (`run_tests` then `trace`): A1's `trace` does not return pass/fail and `_judge` is private. Worth a shared call if latency ever matters more.
9. **Evidence wording.** The fixer sentence comes out as "Changing only swap with temp makes every test pass." or "Changing only delete semicolon makes every test pass." because R1's rule names are written for the table, not for the sentence (`f_fix` template is `Changing only {fix_desc}`). Cosmetic; belongs to F3/R1.
10. **Probe prompts** in `ml/data/probes.json` ("What is the index of the last valid cell of a?") differ from the fixture text ("Index of the last valid cell?"). The live text is used.
11. **Hard-twin ordering.** The first probe offered is `P_T1_b`, not `P_T1_a` (fixture and D1's note), because the posterior is slightly asymmetric (M01 0.368 vs M08 0.352) and EIG picks the better one.
12. **Not checked:** `two_bug` and `novel` with real programs (they occur on some dataset rows in the latency run, status not asserted); the older planet problems (P18–P23) beyond a gate-failure request; behaviour with several workers (caches and the attempt store are per process).

It wrote `ml/artifacts/diagnoser_40e8e6ff/` and the cached matrix `ml/data/features_8e7504692da1.npz`; nothing else outside S2's paths. `ml/artifacts/diagnoser_*` is not in `.gitignore` (M1's note). The `latest()` rule picks the newest folder, so a later retrain by another package changes what S2 serves.
