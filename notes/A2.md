# A2 — gcc stand-in

## Built

- `ml/oracle/gcc.py`
  - `run_tests(problem, code, sample_only=False)` → `schemas.RunResult` with `backend: "gcc"`. This is what `ml.runner.run_tests(..., backend="gcc")` calls.
  - `observe(problem, code, arg_lists=None)` → everything measured per test (`status, error, returned, printed, array0, effects, max_depth, calls`). `problem` only needs `signature`, so other packages can ask "what does real C do with this?" for an ad-hoc function. A3 uses it for its cross-checks.
- `ml/oracle/rl_support.c`: the C side (bounded printf, world builtins as counters, call-depth hooks, padded argument arrays, fault handlers, report writer). Compiled once per Python process.
- `ml/oracle/selfcheck.py`: `python -m ml.oracle.selfcheck`.
- `tests/A2/test_gcc.py`: 34 tests.

## How it works

1. The learner's file and a generated `main` are one translation unit. `main` takes a test index and calls the entry function (name, parameter types and return type come from `problem["signature"]`) with that test's `args`.
2. No system header reaches the learner's code: `#include` lines are blanked (as the interpreter does), `printf` is a macro for a bounded buffer, `strlen` and the world builtins are declared by hand. This is on purpose: mingw headers define `max`, `min`, `small`… as macros, which would break ordinary learner code.
3. Each test runs in its **own process**, all tests in parallel, each with a wall-clock limit (`TEST_TIMEOUT_S = 2.0`). One crashing or looping test does not lose the others.
4. Flags: `-std=gnu99 -O0 -w -fno-builtin -finstrument-functions`.
5. Temp files: one `relearn_gcc_*` folder per Python process in the system temp folder, holding `rl_support.o` and a `run_*` subfolder per call. The `run_*` folder is deleted when the call returns; the process folder is deleted at exit.

## Decisions (where the plans are silent)

| Topic | Decision |
|---|---|
| `status` of a run | `ok` when every test ran to its end (passing or not). Otherwise how the **first** test that did not ended, in test order. `parse_error` when gcc rejects the file. |
| `expected` / `got` | `expected` is the test's whole `expect`. `got` has the same keys with the measured values, except `max_depth_le` → `max_depth`. When a test did not end normally `got["error"]` says why: `time_limit`, `output_limit`, `depth_cap_hit`, `div_zero`, `segfault`, `stack_overflow`, `crash_0x…`, or `line N: <gcc's first error>`. |
| Floats | `returned` and `array0` cells compare within `FLOAT_TOLERANCE` (1e-3) when either side is a float; ints compare exactly; `printed` compares exactly. |
| Python `str` arg | `char[]` with a `'\0'` terminator. A one-character `str` for a scalar `char` parameter becomes that character's code. `array0` of a `str` argument is compared as a string when `expect.array0` is a string. |
| Argument arrays | Live in a heap block with 64 guard cells on each side, filled with `GARBAGE` (−858993460) for `int` and `0xCC` for `char`. So a read just past the end returns `GARBAGE`, as the interpreter does, and a write just past the end does not crash. `i <= n` on P03 returns −858993448, the same number as `tests/fixtures/traces/p03_le_oob_read.json`. Reads further than 64 cells away, and out-of-bounds use of **local** arrays, are plain undefined behaviour. |
| Recursion depth | Measured with `-finstrument-functions` (entry call = depth 1, same as the interpreter's `max_depth`). `max_depth_le` is checked, not ignored. Depth above `DEPTH_CAP` (100) ends the test as `timeout` / `depth_cap_hit`, matching 03 §2.2. |
| World builtins | C stubs that count calls. Effect keys: `fire`, `launch`, `door_open`, `door_closed`, `scan`; `open_door` / `close_door` are accepted as aliases. `call` (number of user-function calls) is also checkable. |
| `scan(int x)` | Returns 0. 03 does not say what it returns. |
| Endless printing | printf output is capped at 64 KB; beyond that the test ends as `timeout` / `output_limit`. |
| Forbidden builtin | If the code calls a name in `problem["forbid"]` (e.g. `strlen` in Q13), nothing is compiled and the result is `status: "unsupported"`, 0 passed. |
| Learner's own `main` | Renamed out of the way; it is never called. |
| Problem-file mistakes | An unreadable `signature`, or a test whose `args` count differs from the parameter count, raises `ValueError` (the author's bug, not the learner's). |
| Result cache | Finished runs are remembered per process (256 entries, keyed by the generated C file). A wall-clock time-out is never remembered. `gcc.clear_cache()` empties it. |

## Skipped / not possible with gcc

- **No trace, no events, no step cap.** An endless loop is caught by the clock (2 s), not by the 5,000-statement cap.
- **Effects that need the interpreter** (`read_cell`, `read_void`, `write_cell`, `compare`, `ret`): a test that expects them has those keys skipped and listed in `got["unchecked"]`; the other keys still decide pass/fail. A test whose only expectation is one of these would pass on gcc.
- **No subset check.** gcc accepts pointers, `struct`, `switch`, multi-dim arrays. `status: "unsupported"` is only produced for forbidden builtins. Functions from headers other than `printf` and `strlen` (`scanf`, `strcmp`, `abs`, `malloc`…) are undeclared, so they come back as `parse_error`, not `unsupported`.
- **Undefined behaviour is undefined.** Uninitialised locals, far out-of-bounds access, signed overflow and falling off the end of a non-void function give whatever gcc gives at `-O0`, not the interpreter's `GARBAGE`. 03 §2.5 already excludes these from the differential check.
- Float division by zero gives `inf` in C; the interpreter is specified to halt. Only integer `/` and `%` by zero come back as `runtime_error` here.

## Speed (measured on the ML laptop, gcc 15.2 MSYS2 ucrt64)

About 0.35–0.55 s per program (compile ≈ 0.25 s, five test processes ≈ 0.1 s); the first call in a process adds about 1–5 s for `rl_support.c` and a cold disk. An endless loop costs 2.4 s. A compile error costs 0.1 s. This is far from the interpreter's 30 ms budget: fine for checking problem files and for A3's cross-checks, too slow for building the dataset.
