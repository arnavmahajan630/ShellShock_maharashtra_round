## How the expected values were checked

- `cases.py` holds 57 + 9 (string) programs whose result the C standard defines. Each is run twice: through gcc (`test_expectations_gcc.py`, `test_strings.py::test_expected_string_values_are_what_gcc_produces`) and through the interpreter. All 66 pass on gcc 15.2, so those expectations are what a C compiler does, not only a reading of 03.
- Tests of interpreter-only behaviour (events, `GARBAGE`, counters, steps, effects) take their numbers from 03 and `subset.py`. Where such a test also asserts a C-defined value, the same program is in `cases.py` and the test says "gcc agrees".
- Not compared with gcc, as 03 §2.5 says: uninitialised reads, out-of-bounds access, int overflow, string-literal comparison.

## Running

```
python -m pytest tests/A3 -q                     # everything
python -m pytest tests/A3 -q -m "not strings"    # without the string tests (or set RELEARN_SKIP_STRINGS=1)
```

With no interpreter (`ml.runner.available("interp")` false), the 200 interpreter tests are **skipped** and the 70 that need only gcc or nothing still run and pass: `70 passed, 200 skipped`. The suite never fails because the interpreter is missing. If gcc is missing too, the gcc tests are skipped as well.

## Not verified

- **The 200 interpreter tests have never run against a real interpreter**; package A1 is not in this worktree. To catch mistakes in the test code I ran the suite once with a scratch shim that answers as "interp" using gcc (no steps, no events): 186 passed, 2 xfailed, 82 failed, and every failure was at an assertion that needs a real trace (events, effects, steps, loop/branch counters, `GARBAGE`, `unsupported`). So the C-defined half of each test is exercised; the lines after the first trace assertion in those 82 tests have only been read, not run. The shim is not in the repo.

## Readings of the spec that A1 may dispute

These are places where 03, `subset.py` and `notes/W0.md` do not fully decide the behaviour. The tests take the reading below; if A1 took another one, one of the two changes — it is not automatically an interpreter bug.

1. **Forbidden `strlen` and rejected constructs → `status: "unsupported"`**, from both `run_tests` and `trace` (03 §2.2 row 21 says only "not executed").
2. **`%` by zero is a division by zero** (`runtime_error`, `div_zero`). gcc traps on both.
3. **Depth cap boundary:** 100 frames finish, 101 do not ("deeper than 100").
4. **An ignored out-of-bounds write gives no `write_cell` effect.**
5. **Void entry function → `returned` is null.**
6. **`steps` has exactly 2,000 entries when `truncated` is true.**
7. **A division by zero ends that test only;** the other tests still run and `per_test` shows `["ok", "runtime_error", "ok"]`.
8. **`intdiv` is emitted for every int / int**, exact or not (`remainder_nonzero` says which). `into_float` is tested for a float declaration, a float assignment and a float return.
9. **The step cap is per test** (4 tests of ~2,100 statements each all end `ok`).
10. **`trace.returned` / `trace.printed` are the recorded test's.**

Deliberately **not** asserted, because the contract is open:

- Whether `if` / `while` get their own step, and where it sits relative to the body. `subset.py` says a step is recorded when its statement *finishes*, but the W0 fixtures put the `if` / `while` step at the condition. Exact step sequences are asserted only for a `for` loop with a one-statement body and for straight-line code.
- Whether a variable appears in `vars` (as null) before its declaration is reached. The W0 fixture does this (`i: null` at step 0). The tests accept both.
- Which step carries the entry function's `call` effect when the first statement itself calls a function.
- How many `empty_body` events a loop with an empty body gives (one, or one per iteration): at least one is required.
- `trace.status` when tests end differently (the W0 fixture builder uses the first non-ok status).
- The `ret` value of a void function, the return value of `scan(x)`, `array0` for a `str` argument, float division by zero, `into_float` for an int / int passed as a float argument.

## Problems found in the contracts

- `subset.py` step rule "a step is recorded when its statement finishes" contradicts the hand-written fixtures for `if` and `while` (see above). One of them should be made explicit.
- 03 §2.2 row 21 gives no status for a forbidden builtin; the natural one (`unsupported`) is assumed.
- 03 §2.3 does not say how `array0` is reported for a `char[]` argument (string or list of codes, with or without the terminator).
- `tests/fixtures/traces/*.json` are compared strictly on status, values, events and counters, and softly on steps: a step difference is reported as `xfail` with a "rebuild the fixture" message, following `notes/W0.md` ("the interpreter and 03 win").
- `test_performance_budget` asserts the 30 ms budget of 03 §2.5 on P03 (best of 7 runs). It can fail on a busy machine.
