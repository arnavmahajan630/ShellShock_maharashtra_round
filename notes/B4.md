## How an item is made

**DeepSeek never supplies an answer.** For each exercise it writes two fragments:

- `code`: what the learner sees, containing one mistake;
- `belief_code`: the program a learner who holds that mistake thinks they are reading (the same code with the mistake "made true", for example `<=` read as `<`).

`build_quiz.py` runs both. The correct answer is what `code` gives; the belief answer is what `belief_code` gives. A candidate is dropped when either fragment does not run, when the two give the same answer, when gcc disagrees with the interpreter, or when the shown code does not actually contain the mistake. That last check uses the interpreter's own events: an M06 item must trigger `assign_in_cond`, M07 `empty_body`, M04 `intdiv`, M05 `uninit_read`, D07 `discarded_call_value`, D08 `str_literal_compare`; M02, D05 and D06 items must never end.

Of 272 candidates, 250 ran and held up; 115 were picked.

`reasoning` items are built from the same pool as `predict_output`: the question states the real output and what a classmate expected, both taken from the runs, and asks why.

## Verifier result

`VERIFY PASSED`. 115 of 115 run on the interpreter; 104 also agreed by gcc; 11 are interpreter-only because C leaves them undefined (uninitialised reads, reads past an array), and those have `verified.gcc: false`. 128 belief answers confirmed by running the believed program. 13 collision items. No item is marked `manual`.

## Decisions (where the plans are silent)

1. **Concept** is one of the five planets or five sectors in `classes.py`, fixed per mistake (M01–M03 loops, M04–M05 variables, M06–M07 conditions, M08 arrays, M10 functions, D01–D02 searching, D03 array_tech, D04 sorting, D05–D07 recursion, D08 strings).
2. **No concept-only items.** Every item has code that runs, so none needs the `manual` flag. The verifier still supports it.
3. **Shared option wording:** `never stops` (the run does not end), `unpredictable` (C leaves the value undefined).
4. **`next_state` on code that never ends** is allowed: the question is about a moment during the run. If the queried line is never reached that many times, the answer is `never stops` (one item, `qz_d05_ns_01`).
5. **A `state_query` line must be a plain statement inside braces.** A loop header runs several steps per pass on the interpreter; the gcc cross-check catches any item that breaks this.
6. **Collision items are hand-written.** Each has one wrong option that two mistakes both lead to (M01/M08 ×5, M02/M07 ×2, D02/M02 ×2, D05/D06 ×2, D01/M03 ×2). Four of them are yes/no questions ("Does this loop ever end?") because that is where two different beliefs meet on one answer.
7. **D02 items may end.** DeepSeek wrote bounded loops (`for` with a fixed number of steps around `low = mid;`), which still give a different result from the believed program. Only M02, D05 and D06 are required to run forever.
8. **M10 drafts were redone.** The first guide described the believed program as "returns instead of prints". A learner who thinks printing hands the value back still sees the print, so for "what does this print" the belief answer was wrong. The guide now says "still prints and also returns". The two M10 `mcq` items are hand-written, because every drafted one put the function call inside the hidden print.
9. **Explanations** are written by `deepseek-v4-pro` with hidden reasoning on. Each call is given the verified answer and facts measured by the interpreter (how often each loop ran, final values, which line read an unset variable). The first pass used `deepseek-flash` without those facts: 7 of 115 explanations were wrong because it traced the code itself and got it wrong. After the change I read all 115 again and found none wrong.
10. **Extra files** beyond the package's "Owns" cell: `ml/items/snippet.py`, `build_quiz.py`, the four `quiz_*.json` source files, `ml/data/quiz_checks.json`.

## Not verified, or weaker than it looks

- **A believed program is a reading of the wrong belief, written by DeepSeek or by me.** Running it proves the belief answer follows from that reading. It does not prove students with that mistake give that answer. No learner has answered these items.
- **Quality was checked by reading.** I read all 115 items and all 115 explanations once each. One draft was rejected (`D05_predict_output_3`: it shows the D06 surface). A second reader would likely find more to argue with.
- **Items for one mistake look alike.** D05, D06 and D07 each have essentially one code shape, so their items differ mostly in names and numbers.
- **Collision items lean on judgement.** That an M02 learner and an M07 learner both answer "yes" to "does this finish?" is my reading of the two beliefs. E17 is the experiment that tests whether the "why?" follow-up separates them.
- **The human skim of 06 §5** (a person reads the DeepSeek-drafted items) has not been done by a human.
- **Difficulty** (61 easy, 41 medium, 13 hard) is the drafter's estimate, unpiloted.
- **Strings:** 6 items have concept `strings` (D08). They run on both backends.

## For other packages

- **The app must show fragments as the body of a function.** A learner who reads `int total;` as a global would rightly say it starts at 0. The first explanation pass made exactly that mistake.
- **`next_state` items need line numbers** next to the code; the question refers to them.
- **D3 (quiz selector), S3 (routes):** read `quiz_items.json` only. Send `PublicQuizItem` fields; never `correct`, `belief`, `explain`, `classes`.
- **`ask_reason`** (05 §4): `verify_quiz.collision_answers(item)` returns the wrong options shared by two or more mistakes.
- **E-c:** E18 can now run its quiz half (`verify_quiz.run_problems`, `target_problems`). E17 has its 13 collision items but still needs the Bayes layer and labelled "why" sentences for them.
- **T1 second pass:** the 115 items can serve as extra contexts for reason sentences (`notes/T1.md`, decision 4).
