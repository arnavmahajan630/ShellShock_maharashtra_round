## How an item is checked

The item's own `code` is what runs: what the learner sees is what was verified. `snippet.py` wraps the fragment into a program without moving any line, and a hidden `tail` (for example `printf("%d", x);`) makes the answer visible.

1. The answer from the interpreter must equal `correct`.
2. gcc must give the same answer wherever C defines what the code does. When the interpreter sees a read of a variable with no value, or a read or write outside an array, the answer is "unpredictable" or "outside the array" and gcc is not asked, because C leaves that undefined.
3. `belief_code` in the check is the program a learner with that mistake thinks they are reading (the same code with the mistake "made true"). Its answer must equal the item's belief answer for that class. So belief answers are also run, not only typed in.

Result on this laptop: `VERIFY PASSED` in about 13 s. 56 of 57 correct answers run; 103 fragments also agreed by gcc; 7 are interpreter-only (undefined in C); 54 of 74 belief answers confirmed by running the believed program.

## Decisions (where the plans are silent)

1. **Code is made runnable.** The plan's tables abbreviate (`for (i = 0; ...)` without declaring `i`, "with a = {2, 5, 9}" in words). The files declare everything, so the fragment runs as shown. Search probes and traps are a small `find(a, n, x)` function plus the array.
2. **`-1` is written with a plain minus sign**, not the typographic one in the plan, so it equals what the code prints.
3. **Trap D02** shows "2" as the correct option, not "2 (stuck)": the hint would give the answer away.
4. **Checks live in a separate file** because the item shapes in `schemas.py` allow no extra fields.
5. **Exam items must not share code with a trap or a probe** (03 §6.6); the verifier enforces it.
6. **26 exam items, not 24.** M04 had no natural place in the five sectors, so searching has a sixth item (midpoint with integer division).
7. **State questions** ("what is s at the end of the last pass?", trap M03) are answered from the interpreter's steps; on gcc a print is added after the queried line.
8. **`ml/items/snippet.py` reaches into the gcc stand-in** for one thing: a state question on code that never stops ends the gcc run at the queried moment by calling the stand-in's own report functions (`__rl_stop`, `__rl_ret_int`, `__rl_finish`). If A2 renames those, this breaks loudly (gcc compile error).

9. **Twin set T5 (M09 ⟷ M10) has no probes.** M09 is a Strong class: it has display text and a twin set in `classes.py` (added upstream for the rule-based stand-in server) but is not a model label. The verifier asks for probes only for twin sets whose members are all model classes.

## Not verified, or weaker than it looks

- **`P_T1_a` is not run** ("index of the last valid cell of `int a[5]`"): a fact about declarations, nothing to execute. Checked by hand.
- **20 belief answers are not run.** 14 are probe entries where the class's answer is the correct answer (the twin that does *not* hold the belief; nothing to run beyond the code itself). The rest are `xt_sort_4` (both classes think `a[j + 1]` is "the last cell"), `xt_str_1` (the plan's `strlen("abc")` with M01 answering 4), and the two entries of `P_T1_a`. These come from the plan or from my reading, not from a run.
- **A believed program is my reading of the wrong belief.** Running it proves the belief answer follows from that reading; it does not prove real students answer that way. Only data from learners can show that.
- **Exam items are hand-written and unpiloted.** Difficulty 1–3 is my estimate.
- **Strings.** The 5 string items and trap D08 run on both backends; if strings are dropped (06 §2), remove `xt_str_*` and note that D08 then has no exam item.
