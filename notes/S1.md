## Endpoints

All responses carry `model_version: "store-v1"` and `latency_ms`. Errors are `{"error": "..."}` with 404/409/422/500/503, no stack trace.

| Endpoint | Request | Response |
|---|---|---|
| `POST /learner` | `{callsign}` | `{learner_id}` (`lrn_<10 hex>`). New learner: all 17 classes `UNSEEN`, `p_active` 0.10. |
| `POST /learner/{id}/seed` | - | the `Learner` object. Resets `{id}` to the demo learner and creates it if unknown (so `demo-learner` works). Keeps the callsign of an existing learner. Deterministic: M01 STABLE 0.08, M06 MASTERED 0.04, M08 ACTIVE 0.90, 14 UNSEEN, 12 attempts, 8 nodes. |
| `GET /learner/{id}` | - | `{learner_id, callsign, misconceptions{17}, nodes{}, attempts[]}` (validates as `schemas.Learner`). 404 if unknown. |
| `POST /reassess` | `{learner_id, class, item_id, item_type, result}` | `{state, p_active, conditions[3], resolved_level, next_item}` (03 8.4) |
| `POST /intervene` | `{learner_id?, attempt_id?, class, modality?, problem_id?, code?}` | R2's package + `learner_state {state, p_active, interventions}` when a learner is given. **See the conflict below.** |
| `POST /learner/{id}/intervene` | same, learner in the path | same. Always reachable. |
| `POST /learner/{id}/attempt-result` | `{attempt_id, problem_id, passed, total, status, top?, top_p?, latent?, exposure?, code?, node?}` | `{updates: [{class, p_before, p_after, state, kind}]}`. **Not in the contract** (see "Added"). |

### `/reassess` rules

- `item_type`: `trap`, `transfer_code`, `same_family_code`, `ghost`, `exam_code`, `exam_trace`, `belief_mcq`, `mcq`, `probe`, `predict_output`, `next_state`, or `intervention_done` (no evidence, only finishes the intervention). Each maps to a row of `knowledge.update_p` / `params.ITEM_GUESS_SLIP`; the response says what changed in `p_active` and `state`.
- `result`: `{correct | passed: bool, hint?, answer?, correct_answer?, family?, problem_id?, name?, belief?: {class: answer}, intervening_levels?, exposure?}`.
- A `TREATING` class that gets any reassess item is taken as having finished the intervention: `P <- P(1 - 0.35)`, state `PROBATION`, and the trap/transfer checklist starts over.
- **An `ACTIVE` or `RELAPSED` class that gets a probation item (`trap`, `transfer_code`, `same_family_code`, `predict_output`) or `intervention_done` is treated as started and finished** (evidence line "Intervention taken as completed (not recorded)"). Reason: `POST /intervene` may have been answered by the stateless route (conflict below), or the app may skip it; without this the class could never leave ACTIVE. This is what makes "seed -> reassess -> STABLE" possible with two `/reassess` calls: M08 0.90 -> 0.585 (learning step) -> 0.190 (trap correct) -> 0.077 (transfer correct), STABLE.
- Probation checklist (kept in `knowledge.log_json.flags`): `trap_passed` set by a correct `trap` (or a `predict_output` whose `belief` names the class), `transfer_passed` set by a correct `transfer_code` whose problem family is in the class's 03 8.3 list and is not the family where it was found (`state_machine.is_transfer`). The family comes from `result.family`, else the bank problem named by `result.problem_id` or `item_id`; if it cannot be found, the item is accepted. Passing a same-family problem is reported as "does not count". `STABLE` needs P < 0.15 and both flags (D2's `next_state`); a transfer alone never makes STABLE.
- A wrong trap after the learning step usually pushes P over 0.5 and PROBATION falls back to TREATING (D2's arrow); `next_item` is then null and the next `/intervene` takes the next modality (`tried` is `knowledge.interventions`).
- `ghost` from STABLE/MASTERED: forgetting `P <- P + 0.05(1-P)` per `result.intervening_levels` (default 0), then the ghost row. Passed with P < 0.10: MASTERED. Failed: RELAPSED.
- `next_item`: only for PROBATION. The class's trap `trap_<class>` (from `ml/data/items.json`) unless already asked in this probation, then the first bank problem (sorted by id) from another family of the 03 8.3 list not yet asked. `{item_id, item_type}`. A failed trap is not re-offered (the second trap pool, predict_output quiz items, is S3's).
- `conditions[].detail`: `"0.19"`; trap: `answered: <answer>` or `predicted 9, actual: outside the array` (the correct answer comes from `items.json` when the request omits it); transfer: `P08 last_beacon`; else `not attempted yet`.
- `resolved_level` is `STABLE` or `MASTERED` when the new state is one of those, else null.

### `/intervene` rules

- Needs a problem and the code: either `problem_id` + `code` in the body, or an `attempt_id` that the store knows (`store.record_attempt(..., code=...)`) or S2's in-memory attempt store (`routes/attempt._recall(attempt_id)["analysis"].code`, tried inside a try/except because S2 owns it).
- Calls `interventions.build_package(problem, code, cls, tried=<modalities already used for this learner and class>, modality=<request>)` in a thread pool. Needs the interpreter; 503 without it. Only problems in the ML bank (`pipeline.get_problem`).
- With a `learner_id` and a misconception class: the modality is stored in `interventions`; `ACTIVE` or `RELAPSED` -> `TREATING`. Other states keep their state (an `UNSEEN`, `STABLE`, `MASTERED` or `PROBATION` class is served a package but not moved). The family of the problem is remembered as `found_family` the first time.
- A problem outside the bank but in `server/fixtures/problems.json` (P18-P23) is answered by the older `routes/intervene.py` function (called directly, lazily imported); anything else is 404.

## The `/intervene` route conflict (for I1)

- `routes/intervene.py` (from Arnav's earlier build, stateless, rule-based, no package owns it) and `routes/learner.py` both register `POST /intervene`.
- `main.py` includes routers in `pkgutil.iter_modules` order (alphabetical): `attempt, intervene, learner, probe, trap`. Starlette answers with the first match, so **`intervene.py` wins today** and the learner-aware `/intervene` in `learner.py` is shadowed. I cannot change that without editing `main.py` (or renaming a module I do not own), and I did not monkey-patch the other router at import time.
- Decision: register the learner-aware handler at `POST /intervene` anyway (it becomes live the moment `routes/intervene.py` is removed, with no other change) **and** at `POST /learner/{learner_id}/intervene`, which nobody else has and which works today. `test_intervene_conflict_status` pins this: if `intervene` is in `LIVE_ROUTERS` it must be the winner, otherwise `learner` must be.
- What breaks in the meantime: a call to `/intervene` with `learner_id` gets the old stateless answer (`model_version: "rules-v1"`, no `learner_state`, no state change, no `tried` list). `/reassess` still works afterwards because of the implicit-intervention rule above.
- For I1: either (a) delete `routes/intervene.py` (nothing else imports it; it imports `RULES_BY_ID, _find_problem` from `attempt.py`, which S2 kept) and the contract path is S1's, or (b) have the app call `/learner/{id}/intervene`. With (a), the P18-P23 fallback inside `learner.py` stops working (it calls `intervene.py`); in that case P18-P23 get 404. If P18-P23 matter, move that function (`_intervene` in `intervene.py`) into a module S1 may own, or add those problems to the ML bank.
- `routes/probe.py` and `routes/trap.py` are not S1's. `trap.py` (`GET /trap-items/{class}`) does not overlap anything of mine.

## Added beyond the brief

- `POST /learner/{id}/attempt-result`: nothing in the plan records an `/attempt` outcome into the knowledge table, and S2's `/attempt` keeps attempts only in memory. This endpoint (or `store.get_store().apply_attempt_result(...)`) is how I1 / the app can: log the attempt, run the 03 8.2 update (failed task with top-1 = k and status `confident`/`two_bug` and `top_p >= 0.5` -> `signature_failure` with the problem's authored exposure for k, default 0.5; pass with `latent` = k -> `latent_pass`; ambiguous, novel, correct, gate -> logged, no P change), move the state (UNSEEN -> ACTIVE at 0.5, STABLE/MASTERED -> RELAPSED), and set a node (`done` + 3 stars on a pass, `unstable` otherwise). S2 did not call it; I did not touch `attempt.py`.
- **Prior hook for S2.** `pipeline.learner_prior_fn` (S2's hook, `None` by default) is set to `store.get_store().prior` when `routes/learner.py` is imported and nobody set it before. It returns `{class: P(active)}` for a learner with any history and `None` for an unknown learner, a fresh one, or when the database file does not exist yet (it never creates the file). Effect on `/attempt`: a seeded learner's M08 prior 0.9 is used by `ml.bayes.prior`. Not tested end to end against the diagnosis (S2's tests use `learner_id: "t"`, which gets `None`).
- `store.py` public methods other packages can call: `get_store()`, `create_learner`, `seed`, `get_learner`, `get_entry`, `prior`, `record_attempt`, `get_attempt`, `set_node`, `apply_attempt_result`, `start_intervention`, `reassess`, `log_event`, `events`, `choose_next_item`, `trap_item`.

## Decisions where the plans are silent

1. `knowledge` columns: `p_active, state, times_seen, last_tested, recheck_queued` plus `log_json = {evidence, interventions, flags}`; evidence keeps the last 20 items. `flags` (found_family, trap/transfer checklist, items asked in this probation) is private and not in `GET /learner`.
2. Seed attempt ids are `at_001..at_012` for `demo-learner` and `<learner_id>:at_001..` for any other id, because `attempt_id` is the table's primary key. The seed's 12 attempts and 8 nodes are made up around the fixture's 3 attempts and 5 nodes (same ids and values for those).
3. `times_seen` counts diagnosed or reassessed items for that class, not intervention requests.
4. The learning step ℓ is applied when the intervention is finished (first reassess after TREATING), not when it starts.
5. A seeded STABLE/MASTERED class has the checklist flags already set, so its `/reassess` conditions read as met.
6. `GET /learner/{unknown}` is 404 (the fixture answered with the demo learner for any id).
7. Thread safety: one lock per store object and a connection per call; fine for one uvicorn process, not for several workers writing the same file at the same moment (SQLite's own locking still protects the file).
8. `pipeline._problems()` (private in S2's module) is used to list the problem bank for `next_item`; `pipeline.get_problem` for single lookups.

## Skipped / faked

- Nothing is faked in the store. The seed is made-up data by design.
- Not done: `exams` table (S3/D3's: 03 11.3 says "SQLite v3 adds `exams`"; this store has no table for it, and `events` can carry exam logs meanwhile), ghost-return scheduling (`recheck_queued` is stored, nothing queues), the second trap pool (predict_output quiz items) in `next_item`, the `max(P, ...)`-free exam updates (D3 calls `knowledge.update_p` itself).
- `intervention_done` is a non-contract `item_type`; no separate "complete intervention" endpoint exists in 03 11.
- Not checked: several uvicorn workers; a database from an older schema (no migrations, `CREATE TABLE IF NOT EXISTS` only).

## Contract problems

- 03 11 gives `/intervene` `{learner_id, attempt_id, class, modality?}`, but S2 keeps attempts only in memory and does not store the code, so a restarted server cannot resolve `attempt_id`. Workaround here: accept `problem_id` + `code` too (the app already sends them to `/probe/answer`) and look the attempt up in the store first. `attempt-result` with `code` makes the store able to resolve it.
- `schemas.KnowledgeEntry` has no room for the probation checklist, so `/learner` does not show which condition is met; only `/reassess` does.
- `ReassessResponse` has no `p_before`; the app sees only the new `p_active`.
